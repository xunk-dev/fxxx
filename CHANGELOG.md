## Unreleased

Not built or run on a device here.

- Frame counters stay live while extracting. `ExtractingScreen` reloaded the Frames state only once per 50 extracted frames, so the header count and the tab counts (All, Favorites, Items) froze at the first value (for example "0 frames" beside 5 on the All tab with 40 cells on screen) while the grid, which reads the database directly, kept growing. - Frames screen shows predicted placeholders while extracting: after the frames already extracted, up to six rows of pulsing empty cells (`FrameSkeleton`, same pulse and reduced-motion rule as `ThumbPlaceholder`) stand for the frames still to come, counted from the extraction total minus the cells already in the grid, and each one is replaced by its real frame as it arrives. - Sharpest shows results progressively and scans faster. The sharpness pass (`FrameSharpnessAnalyzer.scoreProject`, duplicates hashing) now decodes and scores 2 to 4 frames at once (`FrameScan.mapThumbnailsParallel`, order kept for the motion estimate) and reports progress, shown as "Analyzing sharpness… done/total". As soon as every frame is scored, the sharpness-only pick (`onQuick`) is written and shown, so the grid appears without waiting for faces; face weighting then runs in the background and replaces the list in place when it finishes (`refining` state; cache is marked only after the final list). Not built or run on a device here.

- Sharpest filter no longer loads forever, and the other smart filters no longer die behind it. Cause: every ML Kit wait (`Task.await`) ignored cancellation and had no timeout, and the sharpest pass scored faces for dozens of frames one after another with no budget, so a detector whose Play services model was not ready kept `analyzing` true for good; while it was true `applySmartFilterImpl` returned silently, so Key moments, Duplicates and Frames without people did nothing. Fixes: `Task.await` is bounded (12 s, `DetectorTimeout`, an ordinary exception every detector already handles); face weighting in the sharpest and duplicate passes is bounded per frame (6 s) and overall (25 s), runs two frames at a time and uses what it has when the budget ends (`FaceScanner.assessFrameBounded`); a face detector that fails three times in a row is skipped for a minute; `loadSharpest` clears `analyzing` in `finally`, runs off the main thread, captures the project id before the long wait (the result used to be written to whatever project was current afterwards), does not remember an empty result as final and re-runs when the cache says valid but the table is empty; `FramesViewModel` keeps the running analysis job and cancels it on any filter change, a new smart filter replaces a running one, tapping Sharpest again retries an empty or interrupted run, and opening another project resets the screen state and stops the album scan of the old one. Selections no longer swallow cancellation. The analyzing view shows a spinner. `MotionEstimate.bestShift` computed the mean inside its loop (quadratic); it is hoisted. Not built or run on a device here: run `:app:testDebugUnitTest` and try Sharpest, Key moments, Duplicates and Frames without people on a project with faces, with Play services models missing and in airplane mode.

- Ultra HDR JPEG on Android 10 to 13 (API 29-33), no new library and no APK growth. Before, HDR saving was gated to API 34 because the app relied on `android.graphics.Gainmap` and on the platform JPEG encoder writing the gain map. The format itself is plain JPEG (SDR base, a second JPEG with the gain map, `hdrgm` XMP and an MPF index) and is backward compatible, so the app now writes it by itself: `UltraHdrWriter` encodes the base (4:4:4 encoder when possible), encodes the gain map, adds the Container/`hdrgm` XMP to both images and the MPF directory to the base, with offsets and lengths computed from the final sizes. The gain map made by `GainmapBuilder` is kept for older systems in `LegacyGainRegistry` (a weak map keyed by the bitmap, like `HdrSignalRegistry`), and `GainmapOps` (`has`, `copy`, `crop`, `transform`) carries it through edits on every API level. `HdrSupport.supported()` is now API 29 (`MIN_SDK`) instead of 34, `ImageFormat.isAvailable` follows it for Ultra HDR JPEG and 16-bit PNG, and `HdrSupport.platformGainmap()` is the old API 34 check. Limits: below Android 14 the phone itself shows these files in SDR (the HDR rendering needs Android 14+ or a viewer that reads the format, such as Google Photos or Chrome on a newer device); 10-bit decoding still depends on the codec offering P010, and when it does not the frame falls back to SDR as before; the FFmpeg path keeps the API 34 gate. Tests: `UltraHdrWriterTest` (MPF offsets, XMP length, per-channel ranges, JFIF placement), `ImageFormatTest` updated. Not run on a device: check the output in an Ultra HDR viewer.
- Colour regression (extracted frames and snapshots over-contrasty, over-saturated and red-shifted while the player preview is right): the colour calibration (`ColorCalibrator`) judged the first decoded frame of a video, and the library thumbnail loader (`VideoThumbSources.firstFrame`) decodes exactly that frame, which is usually black or flat. A black frame matches every colour reading within the accept limit, so `AUTO` was stored for the video for the whole session and every later extraction and snapshot reused the wrong reading. Fixes: a frame is only used to decide when it has real content (`CalibrationRule.informative`: luma spread and deviation of the 24x24 signature, checked on our own frame before the system reference is fetched and on the reference itself); flat frames do not count as an attempt, are not stored, and the decoder keeps waiting for a better frame (up to 12 per decoder, `FrameDecoder.flatTries`); a decoder that finds a variant already stored by another decoder (parallel extraction, snapshot decoder) adopts it. `ColorCalibrator.calibrate` now returns `Outcome(id, retry)`. Tests in `ColorCalibrationTest`. Diagnostic log line: `ColorCalibrator frame too flat ...`.

- Ads and VPN: turning a VPN on no longer shows the "Can't load ads" notice. - Compression blocking and keyframes in best-frame picking: video codecs leave a grid of block edges (8 to 16 px) that the focus score read as detail, so a blocky frame could beat a cleaner one. `BlockGrid` finds the grid by looking for periodic step energy across columns and rows (the method behind FFmpeg's `blockdetect`, after Muijs and Kirenko; periods 4 to 32, works on cropped video because the phase is measured, not assumed). `BlockAware` scores the frame again with the pixels that straddle those edges left out (`FocusScore.detail(luma, w, h, blocks)`) and turns the ratio into a factor from 0 to 1 that fades in between a grid strength of 0.04 and 0.10, so a frame with no grid keeps factor 1. The factor is measured during extraction on a centred crop of at most 960x540 of the full frame (`BlockProbe`, called from `SampleWriter` and `FfmpegFrameProcessor`) and stored in `projects/<id>/quality/blocks.tsv`, one `index<TAB>permille` line per blocky frame, with no database change (`BlockLedger`); `FrameSharpnessAnalyzer.scoreProject` multiplies the thumbnail score by it, so best frames, the dataset export and smart keyframes all use it. Frames extracted before this change have no entry and keep factor 1. Keyframes are not preferred in general: `KeyframeTie` picks a keyframe only when its score is within 1% of the best frame of the window (`SharpestPicker`, `DatasetSelector`; `ScoredFrame.isKeyframe`). Measured on 288 frames of natural images in five codecs, the share of picks that are close to the best frame rose from 88% to 91%, and in MPEG-4 from 75% to 90%; a fixed keyframe preference did not improve the result consistently (x264 keyframes are slightly better, MPEG-2 and MPEG-4 keyframes are not). The skip-blurry filter of extraction uses the same factor (`ExtractQualityGate`: the history and the new frame are both compared on the corrected scale, and a resumed run seeds its history from the ledger through `GateResume`); it applies to video only (`ExtractRequest.newGate(blockAware)`, animated images pass false) and its effect on the number of skipped frames was not measured separately. Extraction by keyframes needs no change: every frame it keeps is a keyframe, so the tie rule has nothing to decide, while the factor applies as usual.
